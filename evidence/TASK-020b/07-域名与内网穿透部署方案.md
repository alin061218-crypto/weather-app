# 域名与内网穿透部署方案（含演示）

> 背景：Railway 已停用，答辩需要"其他设备也能访问"。你已注册域名。
> 结论：**域名能用，内网穿透能用，而且两者组合是当前最优解 —— 但必须用 HTTPS，原因不只是好看。**

---

## 一、先分清三件事

很多人把这三个混在一起，实际是三层不同的东西：

| 层次 | 是什么 | 你是否有 |
|---|---|---|
| **域名** | 一个人类可读的名字，本质是一条 DNS 记录 | ✅ 已有 |
| **公网 IP / 出口** | 一个能从互联网被访问到的地址 | ❌ 本机在 NAT 后面，通常没有 |
| **持久磁盘** | SQLite 存数据的地方 | ✅ 本来就是本机磁盘 |

**关键认识：域名本身不能让任何东西"能访问"。** 它必须指向一个公网可达的出口。
你有域名但没有公网 IP，所以**必须靠内网穿透把本机接到公网** —— 这就是内网穿透的用途。

---

## 二、内网穿透能实现其他设备访问吗？能

**原理**：本机跑一个客户端 → 与穿透服务商的中转服务器建立**出站**长连接 →
服务商分配一个公网地址 → 外部请求经中转转发到你的本机。
**不需要公网 IP、不需要在路由器上做端口映射**（这也是它在校园网/宿舍网能用的原因）。

但**必须区分两类方案**，答辩场景下差别很大：

| 类型 | 例子 | 老师手机浏览器直接访问？ |
|---|---|---|
| **穿透到公网** | Cloudflare Tunnel、ngrok、花生壳、frp | ✅ 能，输网址即可 |
| **虚拟组网** | Tailscale、ZeroTier | ❌ **不能** —— 对方手机必须也装客户端并加入同一网络 |

答辩时老师不可能为你装客户端，所以**只能用第一类**。这一点很重要，别选错。

### 方案对比

| 方案 | 免费 | 支持你自己的域名 | HTTPS | 备注 |
|---|---|---|---|---|
| **Cloudflare Tunnel（推荐）** | ✅ | ✅ 用自己的域名 CNAME | ✅ 自动签发 | 免费、无需公网 IP、无需备案（节点在境外） |
| ngrok | 免费档 | ❌ 免费档只能用随机域名，自定义域名要付费 | ✅ | 免费档每次重启换地址，演示不便 |
| 花生壳 / 贝锐 | 有免费档 | 免费档域名难记 | 部分 | 国内服务，速度好，通常需实名 |
| frp（自建） | ✅ | ✅ | 需自配证书 | 需要一台有公网 IP 的服务器做中转 |
| **学校/实验室服务器** | 0 | ✅ | 看学校 | **最优解，先问导师有没有** |

**建议：先问导师有没有学校服务器；没有就用 Cloudflare Tunnel。**

## 三、⚠️ 一个功能性的坑：HTTP 下「自动定位」会失效

这不是体验问题，是**功能问题**，必须知道：

> **浏览器的 Geolocation API（`navigator.geolocation`）只在「安全上下文」可用。**
> `http://localhost` 被浏览器视为安全，但 **`http://weather.你的域名.com` 不是**。

后果：如果你用普通 HTTP 暴露到公网域名，**「GPS 定位当前位置」会直接被浏览器拒绝**，
代码里 `main.js:728` 那个 `navigator.geolocation.getCurrentPosition` 拿不到结果，
只能退回到 IP 定位（`/api/location` 兜底）。

**所以 HTTPS 是必需的，不是加分项。** 好消息是 Cloudflare Tunnel 会自动签发 HTTPS，零配置。

（顺带：上 HTTPS 之后，TASK-005 里规划的 `httpOnly + Secure` Cookie 方案才完整可用。）

## 四、推荐方案：Cloudflare Tunnel + 你的域名

### 4.1 架构（关键点：同源，只有一个端口）

```
老师手机 / 答辩电脑
        │  https://weather.你的域名.com
        ▼
Cloudflare 边缘（自动 HTTPS）
        │  隧道（出站长连接，无需公网 IP）
        ▼
你的电脑  cloudflared → http://localhost:3001
                          │
                          └─ node server.js
                             （express.static 托管前端 + /api 同源）
```

**为什么只用一个端口就够 —— 并且这是最优做法**：
`server.js:106` 已经有 `express.static(path.join(__dirname,'frontend'))`，
也就是**后端同时托管前端**。所以同源部署天然成立，`API_BASE` 在非 localhost 下取 `''`（同源）
刚好对上。

**这直接绕开了 P0-9 那个缺陷**：`weather-app/nginx.conf` 里没有 `/api` 代理，
用 nginx 静态托管会导致登录/收藏/历史静默失效。
**所以演示时不要用那份 nginx 配置，直接 `node server.js` 即可。**

### 4.2 操作步骤

```powershell
# 1) 把域名的 NS 交给 Cloudflare（免费套餐），在 CF 控制台添加站点后按提示改 NS

# 2) 安装 cloudflared（winget 或官网下载）
winget install --id Cloudflare.cloudflared

# 3) 登录并授权你的域名
cloudflared tunnel login

# 4) 创建隧道
cloudflared tunnel create weather-demo

# 5) 绑定一个子域名（自动创建 CNAME 记录）
cloudflared tunnel route dns weather-demo weather.你的域名.com

# 6) 写配置 %USERPROFILE%\.cloudflared\config.yml
#    tunnel: <第4步输出的 UUID>
#    credentials-file: C:\Users\<你>\.cloudflared\<UUID>.json
#    ingress:
#      - hostname: weather.你的域名.com
#        service: http://localhost:3001
#      - service: http_status:404

# 7) 启动应用（先起后端的，注意环境变量）
cd E:\weather\weather-project
node --env-file=.env server.js

# 8) 另开一个 pwsh 7 窗口，跑隧道
cloudflared tunnel run weather-demo
```

然后手机浏览器打开 `https://weather.你的域名.com` 即可。

**验收**：用手机（走 4G/5G，不要连你家 WiFi，才能验证真的是从公网进来的）打开网址，
能定位、能搜索、能登录、能收藏。

## 四·补：你的域名（`alin061218.online`，阿里云注册）具体怎么做

### 4.3.1 先确认域名状态（不然后面全是白费）

登录**阿里云 → 域名控制台**，逐项确认：

| 检查项 | 应该是 | 说明 |
|---|---|---|
| **实名认证状态** | ✅ 已实名 | 国内注册商的域名**必须实名**，否则会被置为 `serverHold` —— 域名能改 NS 但**解析不生效**，症状是「配置全对但访问不了」 |
| **域名状态** | 正常 / `ok` | 若显示 `serverHold` / `clientHold` → 先去完成或补充实名 |
| **到期时间** | 覆盖到答辩之后 | 顺手把自动续费打开 |
| **DNS 服务器** | 当前是 `dns*.hichina.com` 之类 | 下一步要改成 Cloudflare 的 |

> ⚠️ **常见误区**：**「实名认证」不等于「ICP 备案」**。
> - **实名认证**：在注册商（阿里云）做，**域名解析的前提**，必须做。
> - **ICP 备案**：在工信部做，**只有当域名解析到中国大陆境内服务器时才需要**。
> 你走 Cloudflare 隧道（节点在境外）→ **不需要备案**。所以本文这条链路你**不用碰备案**。

### 4.3.2 为什么必须先改 NS（而不是在阿里云加个 CNAME）

Cloudflare Tunnel 会给你一个 `<UUID>.cfargotunnel.com` 的隧道地址。**但你不能在阿里云 DNS 里
写一条 CNAME 指过去** —— 因为该地址的解析依赖 Cloudflare 边缘识别 `Host` 头，
只有当**你的域名所在区域（zone）托管在 Cloudflare 上**时才会被正确路由。
免费套餐下必须走「NS 接管」，不能走「部分 CNAME 接入」（那是付费功能）。

所以路径是：

```
阿里云域名控制台 → 修改 DNS 服务器 → 改为 Cloudflare 分配给你们的两个 NS
```

**副作用（正常）**：改完 NS 后，**阿里云云解析里原有的记录全部失效**，之后所有解析都在
Cloudflare 控制台里配。你的域名如果还拿来做别的事（比如指向某个已有网站），要先确认不影响。

NS 生效通常几分钟到 1 小时，最长 48 小时。

### 4.3.3 子域名规划建议

**用子域名，不要占用主域名**：

```
weather.alin061218.online     ← 天气应用
alin061218.online             ← 留给以后别的东西（个人主页等）
```

理由：主域名（apex）以后想指别处会互相打架；而且 `weather.alin061218.online` 在论文里
写出来也比裸域名更像一个正式部署。

`cloudflared tunnel route dns` 会自动创建对应的 CNAME 记录，你不用手配。

### 4.3.4 完整操作顺序（按这个顺序做，别跳）

```powershell
# ── 阶段 1：Cloudflare 侧（网页操作）────────────────────────
# 1. dash.cloudflare.com → Add a site → 输入 alin061218.online → 选 Free 套餐
# 2. Cloudflare 会给出两个 NS（形如 xxx.ns.cloudflare.com）
# 3. 复制这两个 NS 备用

# ── 阶段 2：阿里云侧（网页操作）────────────────────────────
# 4. 阿里云域名控制台 → 找到 alin061218.online → 管理 → DNS 修改
#    → 选「自定义 DNS」→ 填入 Cloudflare 的两个 NS → 保存
# 5. 等 Cloudflare 面板上域名状态变成 Active（通常 10 分钟 ~ 1 小时）
#    ★ 这一步没变 Active 之前，后面全部不要做

# ── 阶段 3：本机侧 ────────────────────────────────────────
winget install --id Cloudflare.cloudflared

cloudflared tunnel login                     # 浏览器授权，选中 alin061218.online
cloudflared tunnel create weather-demo       # 记下输出的 UUID
cloudflared tunnel route dns weather-demo weather.alin061218.online

# 写配置 %USERPROFILE%\.cloudflared\config.yml ：
#   tunnel: <上面的 UUID>
#   credentials-file: C:\Users\Lenovo\.cloudflared\<UUID>.json
#   ingress:
#     - hostname: weather.alin061218.online
#       service: http://localhost:3001
#     - service: http_status:404

# ── 阶段 4：跑起来（两个 pwsh 7 窗口）──────────────────────
cd E:\weather\weather-project
node --env-file=.env server.js               # 窗口 A
cloudflared tunnel run weather-demo          # 窗口 B
```

### 4.3.5 验收（关键：一定要用手机流量测）

1. **手机关掉 WiFi、用 4G/5G**，浏览器打开 `https://weather.alin061218.online`
   —— 这样才能证明请求真的是从**公网**进来的，而不是走了你家局域网。
2. 地址栏应该显示**锁形图标**（HTTPS 生效）。
3. 逐一验证：**自动定位能弹出授权并成功**（这是 HTTPS 是否真正生效的判据）、
   搜索城市、注册登录、收藏、7 天预报、城市指南。
4. 打开 `/admin`，确认带 token 时能看到后台、不带 token 时进不去。

### 4.3.6 你这个组合的额外注意点

| 事项 | 说明 |
|---|---|
| **备案** | ✅ 不用。但**如果以后把域名解析到阿里云国内 ECS，就必须备案（2–3 周）**，届时 NS 可能要从 Cloudflare 改回阿里云 |
| **Cloudflare 免费套餐** | 够用。免费套餐支持 Tunnel、自动 HTTPS、无限流量 |
| **国内访问速度** | 走 Cloudflare 境外节点，国内访问一般可接受；如果演示时觉得慢，改用局域网直连备选 |
| **不要在阿里云同时保留云解析** | NS 改了以后阿里云解析失效，别两边都配，会产生"我明明配了却不生效"的困惑 |
| **域名被墙/污染风险** | 一般不会。若突然访问不了，先用手机流量试，再排查是不是本地 DNS 缓存 |
| **演示当天** | 隧道依赖你的电脑 + 网络 + Cloudflare。**录屏兜底仍然必备** |

## 五、把本机暴露到公网的安全注意事项（重要）

一旦穿透成功，**你的电脑就真的在公网上了**，会被扫描器扫到。演示期间请做到：

1. **只在演示前后开启隧道**，演示完 `Ctrl+C` 关掉。不要长期挂着。
2. **先完成 TASK-005 再暴露**。目前 `/api/login`、`/api/register`、`/api/admin-login`
   **没有任何速率限制** —— 暴露到公网等于开放暴力破解。TASK-005 会加 `express-rate-limit`。
3. **`/admin` 后台会被扫到**。TASK-001/002/003 已经修好鉴权与 XSS，但建议演示时把
   `ADMIN_USER` 改成不好猜的名字、口令用强口令。
4. **不要在这台机器上同时暴露其他服务**（数据库端口、开发服务器等）。
5. **不要在隧道后面放真实个人数据**。演示用数据库可以单独放一份。
6. 若担心，可以用 Cloudflare Access（免费档）给整个站点加一层邮箱验证 ——
   但注意这会让老师也需要验证，答辩场景不合适，除非只保护 `/admin`。

## 六、不备案的完整可行路径

### 6.1 先搞清楚备案到底卡在哪

很多人以为「有域名就得备案」，这是错的。**备案的唯一触发条件是：让域名解析到中国大陆境内的服务器。**

| 场景 | 需要备案？ |
|---|---|
| 域名 → Cloudflare 隧道 → **你的本机** | ❌ 不需要（边缘节点在境外） |
| 域名 → **境外/香港服务器** | ❌ 不需要 |
| 域名 → **阿里云/腾讯云国内节点**，且提供 Web 服务 | ✅ **必须** |
| 只在内网用 IP 访问（不经域名） | ❌ 不需要（压根不涉及备案） |

**关键认识**：备案的执行方是**境内主机服务商和境内 CDN**（阿里云 ECS 会拦未备案域名的 80/443），
**不是域名注册商**。所以你用阿里云注册的域名，只要**服务器不在境内**，就完全不用备案。

### 6.2 三条正规的「不备案」路线

| 路线 | 成本 | 需要电脑常开？ | 持久磁盘 | HTTPS | 适合 |
|---|---|---|---|---|---|
| **A. 本机 + Cloudflare Tunnel** | **0 元** | ❌ 需要 | ✅ 本地磁盘 | ✅ 自动 | **答辩首选** |
| **B. 境外/香港 VPS** | ¥20–30/月 | ✅ 不需要 | ✅ 云盘 | ✅ 自签或用 CF 代理 | 想让它长期在线 |
| **C. 纯局域网**（不用域名） | 0 元 | ❌ 需要 | ✅ | ❌ | 只作现场备用 |

**推荐组合：A 作答辩主方案（0 成本、自有域名、自动 HTTPS），C 作现场备选，录屏兜底。
如果希望它长期在线又不想备案，再上 B。**

#### 路线 A 的取舍
- ✅ 零成本、域名好看、自动 HTTPS、数据在本地不会丢
- ❌ **依赖你的电脑开机 + 网络在线**，关了就访问不了
- ❌ 电脑暴露在公网，需按第五节做安全加固（先完成 TASK-005）

#### 路线 B 的取舍（阿里云香港轻量应用服务器）
你已经在用阿里云，**同一套控制台直接开一台香港节点**即可，运维习惯不用换：
- ✅ **不需要备案**（境外地域）
- ✅ 常在线，不依赖你家电脑
- ✅ 装上 Node + 跑 `node server.js` + 挂 Cloudflare 代理（免费 HTTPS）即可
- ⚠️ 国内访问香港约 40–80 ms，够用；美西节点约 150–200 ms，偏慢
- ⚠️ 要自己配环境（Node、依赖、进程守护 `pm2`/`systemd`）
- **注意**：别买成「内地」地域 —— 那就要备案了，购买时看清楚地域选项

### 6.3 一个能省事的关键设计：先把 NS 交给 Cloudflare

**不管最终走 A 还是 B，都建议先把 NS 交给 Cloudflare。** 原因是它给你两种部署方式之间的**自由切换**：

```
NS 交给 Cloudflare 之后：
  ├─ 走路线 A：建 Tunnel，ingress 指向本机 3001
  └─ 走路线 B：加一条 A 记录指向香港 VPS 的 IP（开小云朵代理）
```

**以后从 A 换到 B，所有改动都在 Cloudflare 面板里完成，不用再碰阿里云。**
这就是为什么第四·补那节的 NS 操作值得先做 —— 它买的是「以后的灵活性」。

（对比：如果只走路线 B 且不介意，也可以**保持阿里云 DNS 加一条 A 记录**，
再用 `certbot` 签 Let's Encrypt 证书，NS 完全不用动。但那样就没有免费 CDN 和源站 IP 隐藏了。）

### 6.4 ❌ 不要做的事（灰色/违规/不可靠）

| 做法 | 为什么不行 |
|---|---|
| 国内服务器 + 改用非 80/443 端口绕过备案 | 阿里云会主动扫描并封禁端口/停机；属于规避监管，**答辩材料里更不能写** |
| 借用别人的备案号 | 明确违规，会被注销并影响信用 |
| 域名解析到国内源站、前面套境外 CDN | 源站在境内，服务性质仍是境内；且是典型的规避手法，不可取 |
| 用临时免费域名（如某些穿透送的二级域名） | 不稳定、不好写进论文，且免费档常换地址 |

### 6.5 结论：你现在该怎么做

1. **答辩演示** → 走**路线 A（本机 + Cloudflare Tunnel + `weather.alin061218.online`）**，0 成本、不备案
2. **如果你想让系统长期可访问** → 加一台**阿里云香港轻量**（路线 B），同样不备案
3. **无论走哪条** → 先把域名 NS 交给 Cloudflare（拿到以后切换的自由）
4. **顺手做**：域名续费覆盖到答辩之后；确认域名实名认证已通过（这是解析的前提，与备案无关）

## 八、这件事在论文里怎么写

部署到自有域名 + HTTPS 是一个**真实的工程交付**，够写「系统部署」一章，而且里面有一个

1. **部署方案选型**：对比「云平台（Railway/Render）」「校园服务器」「本机 + 内网穿透」，

### 8.1 SQLite 持久化与备份清单（TASK-020）

生产部署时必须把 `DB_DIR` 配置到持久卷，不能使用 `%TEMP%` 或容器临时文件系统。SQLite 的 WAL 模式会同时使用 `weather.db`、`weather.db-wal`、`weather.db-shm`，三个文件必须位于同一目录；迁移时先正常停止服务并确认 WAL 已 checkpoint，备份时不要只复制主库。

部署后定期运行 `npm run backup:db`。该脚本通过 SQLite `VACUUM INTO` 生成 `backups/weather-YYYYMMDD-HHmmss.db` 一致性快照，保留最近 10 份，并打印快照大小以及 users、favorites、history、feedback 的行数，便于确认备份可用。

### 8.2 正常停服与 WAL 合并（TASK-020b）

本服务注册了 `SIGINT` 和 `SIGTERM` 处理器。在支持信号投递的平台上，收到信号后打印「正在关闭」，通过 `server.close()` 停止接受新连接并等待在途请求。等待最多 5 秒，超时则终止剩余 HTTP 连接并继续执行 `wal_checkpoint(TRUNCATE)` 和 `db.close()`；成功后打印「已优雅关闭（WAL 已合并）」并以退出码 0 结束。任一步失败会打印错误、继续尝试关闭数据库并以退出码 1 结束。关闭过程中再次收到信号则立即以退出码 1 结束，此时不能依赖 WAL 已合并。

Linux 上使用正常的停止命令（如 `kill -TERM <PID>`、`systemctl stop` 或 `docker stop`），让服务有机会合并 WAL。Docker 的 Node 进程应直接作为容器主进程启动，或由能转发信号的 init 启动，避免 shell 包装截留信号。Compose 建议设置：

```yaml
services:
  weather:
    command: ["node", "server.js"]
    stop_signal: SIGTERM
    stop_grace_period: 10s
```

`stop_grace_period` 建议 **至少 10 秒**，为 5 秒请求排空以及 checkpoint、数据库关闭留出时间。不要使用 `SIGKILL`、`kill -9` 或 `docker kill` 停服务。PM2 的 `kill_timeout` 同样建议至少 `10000`（毫秒），使用 `pm2 stop` / `pm2 restart`；PM2 默认的 `SIGINT` 以及 Linux 上的 `SIGTERM` 都接入相同关闭流程。systemd 建议 `KillSignal=SIGTERM`、`TimeoutStopSec=10s` 或更长。

Windows 下**不要用 `taskkill /F` 停服务**，应在服务所在终端按 **Ctrl+C**，并确认日志出现「已优雅关闭（WAL 已合并）」、进程退出码为 0。`Stop-Process` 即使不带 `-Force`，也不能当作对 Node 的优雅关闭：Windows 实际直接终止进程，`-Force` 不是是否投递 SIGTERM 的开关。不得把 `Stop-Process` 当作 SIGTERM 验收或正常合并 WAL 的保证。运行中备份继续使用 `npm run backup:db`，不要直接只复制 `weather.db`。

**验收限制（2026-10-03）**：SIGTERM 的信号投递为平台行为：Windows 无真实信号（实测处理器不触发）。本机已验证关闭流程本身；SIGTERM 投递将在 TASK-010b 选定 Linux 部署目标后实测。本机另已通过真实控制台 Ctrl+C 验证 SIGINT，包括连续两次 SIGINT 在 1 秒内以退出码 1 结束；不得声称 SIGTERM 已在本机验证。
